## Concrete findings from this pass

### 1. Duplicate event titles need stable display disambiguation

At least two title collisions exist in the authored set:

- E71 — **The Baker's Ledger**
- E112 — **The Baker's Ledger**
- E82 — **Toma's Price**
- E121 — **Toma's Price**

These are not automatically invalid because IDs are stable, but the final UI/localization catalog must not rely on title uniqueness. The content schema must require unique IDs and should support a distinct subtitle/context tag where repeated titles are intentional.

### 2. Some trigger vocabulary is referenced without a source definition in the currently inspected corpus

Examples requiring canonical resolution include:

- E111 references `local_relief_councils`.
- E113 references `full_ledger_published` and `ledger_network_public`.
- E114 references `people_charter_endorsed`.
- E118 uses a broad `Seris >= 0` gate, which is effectively available for almost every normal relationship state and needs deliberate pacing review.
- E127 references `hereditary_seats_limited` and `temporary_noble_exemption`.
- E130 references `infrastructure_concession`.
- E131 references replay metadata `all_voices_heard` that cannot be represented as an ordinary single-run kingdom flag without a defined cross-run persistence contract.
- E133 references `mastermind_hunt`, which conflicts with the campaign's stated systemic-mystery philosophy unless this is explicitly an intentionally misleading investigation hypothesis.
- E185 references `cheap_weapons`; the canonical state must distinguish the purchase decision from the later unresolved durability state.
- E186 references `warehouse_arson` or an equivalent replay unlock; the final schema must define this explicitly rather than leaving an informal alternative trigger.

These are **integration blockers**, not reasons to delete the authored events. They must be normalized into the canonical state vocabulary.

### 3. Replay metadata is currently underspecified

E131 and E186 explicitly depend on information from a previous run. The current `KingdomState` model describes one save/run but does not yet define a persistent cross-run profile/knowledge layer. Before engine implementation we need a separate, versioned `MetaProgressState` (or equivalent) containing only intentionally persistent information. This must not leak arbitrary state from one run into another.

### 4. Delayed consequences are authored inconsistently

Some nodes describe delays in prose (`after 3 turns`, `5+ turns later`, `later`, `during a later crisis`) while others name an event or flag. The production schema therefore cannot be generated by simple text extraction. Every delayed consequence needs:

- source event/choice ID;
- exact delay or condition window;
- exactly-once identity;
- target event/condition or state effect;
- persistence through save/load;
- cancellation/supersession rule where another decision changes the premise.

### 5. Narrative graph and event catalog are not yet one source of truth

`docs/EVENT_GRAPH.md` currently describes causal candidate edges, while event files contain authored triggers and effects. These two layers can disagree until machine-readable canonical data is introduced. The correct next step is to reconcile them, not to treat the graph as runtime truth.

### 6. Resource vocabulary needs normalization before balance simulation

The core state model defines gold, trust, security, power and reputation. Expansion text also uses contextual resources/conditions such as food stability, winter severity, guild leverage, border tension, information trust and food pressure. These must either become explicit derived variables with documented formulas or be replaced with canonical flags/thresholds. Otherwise automated simulation cannot reproduce the narrative conditions deterministically.

### 7. Some choices are intentionally asymmetric but need branch-pressure verification

Examples include emergency authority, private army licensing, military tribunals, border closure, suppression of mutiny, and emergency powers inheritance. These choices can create strong state advantages while damaging trust. QA must test whether they create recognizable alternative routes rather than simply making one ending mathematically dominant.

## Canonical normalization tasks created by this audit

1. Build one event registry E01–E270 with unique IDs and source provenance.
2. Extract every flag/history marker and classify it as `state`, `history`, `thread`, `delayed`, `ending`, or `meta`.
3. Extract every trigger token and resolve it to exactly one producer or explicitly mark it as a derived condition.
4. Define `MetaProgressState` for replay-only information before using replay triggers in engine data.
5. Replace prose-only delayed timing with exact machine-readable windows.
6. Normalize contextual variables such as food pressure and border tension.
7. Detect duplicate titles separately from duplicate IDs.
8. Verify every event has at least one meaningful downstream consequence or deliberate terminal role.
9. Simulate reachability from a fresh state and from representative replay states.
10. Simulate all ending prerequisites and record mutually exclusive locks.

## Gate result

**Content phase remains below READY.**

The 270 authored nodes are a volume milestone, not a verified production campaign. The next major implementation step is canonicalization + static validation, not more event-count expansion unless the audit discovers a genuine narrative gap.
